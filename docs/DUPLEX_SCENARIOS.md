# 双工交互场景与测试案例库

整理日期：2026-11-01；键盘案例于 2026-11-02 按 0.2.0 讨论模式更新。适用于知言键盘插件、相邻的 DSH Realtime Voice 项目，以及后续交互原型。

这里收集的是**交互事件和输入轨迹**：用户没说完时是否等待、附和时是否继续、改变主意时是否改向，以及用户没主动发问时模型是否值得开口。回答内容正确和交互时机正确分别评分。所有面向用户的生成文字仍由当前会话主模型产生，System 1 只决定动作。

下列共 **38 个案例：18 个语音、14 个键盘、6 个探索案例**。台词均为本项目自编，借鉴公开数据的现象分类，不冒充原始数据样本。语音与探索案例保留原设计；键盘的自动提交预期已移除。整套案例尚未批量运行，新版定向验证见 VALIDATION.md。

## MOSS-Live 带来的具体测试启发

1. **听到了多少必须单独记账。** 官方协议区分音频生成结束、音频块实际播完、停止时的部分播放时长。由此设计 V15：模型被打断后，不能把缓存里尚未播出的内容当作双方已经交流过的内容。[协议](https://platform.moss.cn/docs/scenarios/moss-live/)
2. **前台交谈和后台任务分别验收。** 官方模型说明支持将长任务委派后台并继续交流。对应 V08、V16：停止讲话、暂停播报和取消任务是不同动作，短问答也不应偷偷重启原任务。[模型说明](https://platform.moss.cn/docs/models/moss-live/)
3. **保持讲话也是能力。** 将附和、旁人讲话和真正纠正放到相似音量、相同位置测试，避免只测“能不能打断”。对应 V03、V04、V10—V12。

这些是架构与行为参照。MOSS-Live 本身可以生成语音回答，官方上述文档没有证明它能被配置为我们的纯决策层；直接替换当前链路，仍需解决“回答必须来自所选主模型”的要求。本项目可以先采用它启发的测试标准。

## 使用方法与共同判据

- `U` 为用户，`A` 为助手；方括号描述事件，不要念出来。例如 `[停顿 1 秒]`、`[A 开始播报 1 秒后]`。键盘的每个箭头代表一次真实编辑，不是把最终整句粘贴进去。
- 语音先用耳机、安静环境；再对关键样本增加外放、背景人声、快慢语速。保存用户与助手的独立音轨及同一时间轴，不要删除静音或把重叠整理成轮流讲话。
- 每个案例单开会话，固定主模型、人设、推理等级、决策配置。语音记录 ASR 后端；键盘开启“边写边聊”，普通停顿可先取 1.2 秒。需维持忙碌状态的测试用可控延迟的只读模拟工具，避免依赖模型恰好回答得慢。
- “回归”表示当前链路可测，不等于已经通过；“差距”表示目标行为超出当前能力或保障粒度；“探索”表示新交互假设。未实现记为不支持，不混进当前功能通过率。
- 不要求主模型逐字复现某句答案；要求符合语义、说话人身份、人设和时机。已接纳的正式任务不能靠清空草稿撤回；过去的工具执行也不能被后来的改口倒退抹掉。

## 语音案例 18 条

参考类别：H＝HumDial；F＝Full-Duplex-Bench；T＝TurnBench；E＝ECHO；M＝MOSS-Live；“自编”表示工程场景设计。每条同时记录实际动作和最终用户体验。

| ID / 类型 | 输入及插入时机 | 期望与失败判据 | 参照 |
|---|---|---|---|
| V01 回归：思考停顿 | U：“我想找一个适合……[停顿 1 秒] 4060 笔记本跑的识别模型。”分别改成 0.3、0.8、1.5 秒停顿 | 句意未完时等待，后半句进入同一意图；抢答或只按“适合”推荐算失败 | H/F |
| V02 回归：明确交棒 | U：“请用一句话解释语音识别。”自然收尾后安静 5 秒 | 只提交一次并回答；一直等新声音、同一句重复提交分别记录为漏响应、重复提交 | F/T |
| V03 回归：附和 | A 讲三个方案，播报 1 秒后 U 轻声：“嗯嗯，你继续。” | 继续或短暂停后续播，保持原内容和原任务；把附和变成新任务、从头重播算失败。额外记录短暂停次数 | H/F |
| V04 回归：同词不同意图 | 两个会话均在讲解中说“可以了”。前文 A 组约定它表示停止讲解；B 组约定它表示认可前提、继续说明 | A 组让出话轮，B 组继续；两条都对才算一组成功，防止只靠关键词 | E，自编配对 |
| V05 回归：改正条件 | A 正介绍上海行程，U：“不是上海，是杭州，两天就够。” | 停止旧播报，后续回答采用杭州、两天；旧城市音频继续冒出来、只道歉但参数未更新算失败 | H |
| V06 回归：请求重述 | A 讲到第三点，U：“第二点没听清，再说一遍。” | 回到第二点并解释，保持原主题；重复全部内容或继续第三点算失败 | H |
| V07 回归：换话题 | A 讲旅游，U：“先不聊旅行了，解释一下什么是缓存。” | 后续进入缓存主题；旧旅游音频不能在新回答后恢复播放 | H |
| V08 回归：停说与取消 | A 在等只读查询并播报。A 组 U：“先别念了，查询继续。”B 组 U：“取消这次查询，不用继续了。” | A 组仅停播报，B 组停止对应任务；通过任务事件确认，不以一句“好的”当执行证据 | H/M |
| V09 回归：同时开口 | U 在 A 首音频前后约 100 ms 开口：“等一下，我补充一个条件，预算一千。” | 能收全新条件并让用户说完；互抢声音、漏掉“预算一千”、旧回答复活算失败 | F，自编时序 |
| V10 差距：对别人说话 | A 介绍方案；同一用户转向同伴：“小王，帮我拿一下杯子。”随后对 A：“继续刚才的。” | 旁话不成为新任务；恢复原主题。仅靠声纹相同不能判为对助手讲话 | H/F |
| V11 差距：背景人声 | 保持用户安静，另一个扬声器播放“等一下”“好的”等人声；分别在 A 讲话与安静时播放 | 不创建任务、不取消原任务；记录错误停播。与 V05 保持近似音量，避免只依赖响度 | H/F |
| V12 回归：自身回声 | 外放 A 的回答，用户全程不说话；调整音量与设备距离 | A 不把自己的播报转写成用户请求，不自问自答；出现循环或误取消算失败 | T，自编设备场景 |
| V13 回归：口语自我修正 | U：“找周五……不对，周六下午从杭州出发的车次，只查时刻。” | 在模拟查询里使用周六、下午、杭州；保留周五或过早发起错误查询算失败 | F-v3 |
| V14 回归：ASR 修订 | 控制器回放依次注入 partial“请删除日志”→partial“请别删除日志”→final“请别删除日志，只统计大小” | 不根据临时转写执行删除；旧决策失效，最终只读。它是控制器测试，不能当作真实 ASR 准确率 | 自编 |
| V15 差距：只记实际听到的 | A 准备三个带不同数字的方案，播到第一项中间时 U 打断：“刚才说到哪儿了？” | 根据实际播放位置接续，不声称已讲完第二、第三项；同时记录已生成、已排队、已播放的范围 | M |
| V16 差距：后台任务中短交流 | 只读模拟工具延迟 5 秒，期间 U：“你现在查的是哪个目录？” | 主模型能回答当前进度，后台任务不重复启动；结果回来仍连接原请求，不能长期挤占用户说话机会 | M，自编 |
| V17 回归：主动澄清过期 | 开启主动澄清，U：“帮我比较这两个方案。”若澄清开始准备，再补：“就是本地识别和云端识别，按延迟比较。” | 信息不足可请求主模型澄清；补充到达后，尚未播出的“哪两个方案”应失效。不允许猜出不存在的两个方案 | 自编 |
| V18 回归：多轮连续改向 | 依次进行“推荐室外活动”→播报中“改室内”→“嗯，继续”→“刚才第二个再讲一下”→“停止说话” | 每轮保留最新条件，附和不清任务，重述指向用户实际听到的第二项；不混入旧轮音频 | H，自编组合 |

当前语音实现需要重点观察：V01/V02 的 `wait` 没有静默重判定时器，可能出现持续不响应；V03 起声会先暂停，体验上可能产生不必要的顿挫；V10/V11 缺少完整的受话人识别；V15 目前按完整播报片段记账，不能证明句中精确接续；V16 不具备任意后台任务中的独立前台对话保障。具体背景见相邻语音项目的 `docs/TURN_DECISIONS.md` 和 `docs/LATENCY.md`。

## 键盘案例 14 条

这些案例根据现有行为和真实演示自编。必须保留编辑时序：同一份最终文本，经历不同的退格、停顿和回车，会有不同风险。

| ID / 类型 | 编辑轨迹 | 期望与失败判据 |
|---|---|---|
| K01 回归：半句意见 | 输入“我想把第一版做成聊天、日历和社区一体的应用，最好一个周末上线，我还想”→停顿，不按 Enter | 主模型给针对范围或时间的具体意见；不自动执行、不只复述，不改写草稿 |
| K02 回归：讨论口吻 | 用 K01 的草稿触发意见，检查提示框和输入框 | 意见以符合 DSH 人设的助手口吻参与讨论，不扮演用户续写句子；输入框保持原文，提示框没有续写或采纳按钮 |
| K03 回归：完整前句仍是草稿 | 输入“我想知道当前工作区的位置，然后”→停顿→末尾追加“用一句话解释它”→Enter | 停顿时全文保留、没有正式消息；Enter 只发送一条完整消息“我想知道当前工作区的位置，然后用一句话解释它” |
| K04 回归：未完条件与讨论 | 分别输入“我想知道当前工作区的位置是否”和“先别执行，我在想第一版要不要同时做聊天和社区”→停顿 | 前者可以等待，后者允许给取舍意见；两者都不执行。不能因为“先别执行”就禁止讨论 |
| K05 回归：引用不是命令 | 输入“我在写文档，示例是‘删除全部日志，然后重启’，这里措辞有点”→停顿 | 可以给写作意见，不把引号内命令自动提交。用代码块版本重复一遍 |
| K06 回归：决定途中改口 | 输入“我想同时做聊天和社区”→意见请求中改为“我决定只做聊天” | 替换导致旧意见失效，基于新草稿重新判断；若仅追加文字，较早意见可标注保留。全程没有正式任务 |
| K07 回归：清空与迟到结果 | 输入想法→意见请求中全选删除；再在意见已经出现时清空一次 | 草稿、意见、emoji 和悬浮记录全部清空；常驻空框保留，迟到响应不复活 |
| K08 回归：意见请求撞 Enter | 意见生成中继续输入后半句并按 Enter | 取消辅助结果，DSH 只收到一条完整草稿；迟到意见不复活。输入框不经历自动切前句或恢复前句 |
| K09 回归：Tab 原生行为 | 意见出现后分别按 Tab、Shift+Tab；在原生菜单打开时再测试 | 与关闭插件时的原生行为一致；插件不插入文字、不发送消息、不阻断焦点切换或原生菜单 |
| K10 回归：运行中纠正草稿 | 只读搜索任务运行时输入“等等，只查 src 目录，”→停顿→用户手动发送 | 停顿时讨论暂停、原任务不被改向；只有手动发送后才由 DSH 原生处理纠正 |
| K11 回归：运行中追加草稿 | 原任务运行时输入“请统计 README 的行数，然后”→停顿 | 全文留在输入框，不自动排队、不调用决策或辅助主模型；用户仍可原生手动提交 |
| K12 回归：输入法和光标 | 拼音候选尚未确认时停顿；再选中草稿中段或移光标到句中编辑 | 组词、有选区或光标不在末尾时，不启动新预览；插件不插入文字。真实操作系统输入法需人工测 |
| K13 回归：模型、人设和会话变化 | 意见生成途中切换模型或会话；另用两套已有 DSH 人设输入相同想法 | 旧结果不进入新会话；新意见来自新选主模型，措辞遵循生效人设 |
| K14 回归：辅助请求失败 | 在测试适配器中令预览请求超时或断开，再返回迟到意见 | 显示错误且草稿完整保留，同一草稿不自动重试；无正式消息或工具调用。继续编辑可再请求讨论 |

K08、K14 需要控制预览延迟或注入网络故障；K10/K11 需要任务保持运行。它们不再依赖原生前句接纳钩子。

## 探索新交互的 6 个案例

这组用来决定下一步做什么，不要求现有插件通过。研究可提供参照，产品规则由我们提出并验证。

| ID | 场景 | 观察重点 |
|---|---|---|
| X01 持续修改任务 | 用户输入旅行计划，主模型同步形成目标/约束卡；用户只把预算从 3000 改成 1500 | 受影响步骤重新规划，已完成的无关检索复用；用户无需再写完整提示词 |
| X02 提前试做 | 用户输入“我想比较本地和云端识别”时，用户启用只读预计算实验后，主模型预备速度、隐私两个方向；继续输入“只看中文延迟” | 复用相关只读检索，舍弃隐私分支；记录节省时间和废弃计算，所有分支不提前修改用户文件 |
| X03 语音键盘交叉纠正 | 用户说“上海周五”，随即在任务卡改成“杭州周六”；旧 ASR final 之后才到 | 用编辑版本和事件顺序确定权威状态，迟到转写不覆盖键盘纠正，不生成两份请求 |
| X04 环境主动开口 | 用户正写另一段需求，后台测试发现与当前目标相关的失败 | System 1 判断紧迫性，主模型形成一条可操作意见；不因每条日志刷新持续打断用户 |
| X05 相处方式可切换 | 同一段“周末做完三个模块”的草稿，分别选择“陪我想／替我做／先旁听” | 前者质疑取舍，中者在用户明确发送后推进任务，后者记录待议点并保持安静；不能只换文风而行为相同 |
| X06 主动提出分歧 | 用户打到“用户数据全部放本地，而且所有设备无需联网实时同步”，尚未提问 | 主模型指出两项约束的冲突，可提供两条取舍；用户保留某条后，只修订对应假设，不把意见直接执行成改代码 |

## 从案例做成可复现的数据

**语音保存三层材料。** 第一层是真实双轨录音与人工事件标注；第二层是实时音频回放，保留静音、重叠和说话人；第三层才是 ASR partial/final 的控制器事件回放。第三层适合定位决策与生命周期错误，无法验证回声、语调或 ASR。原始用户轨只能按真实时间流入，不能在时刻 t 把后续音频或最终转写提前交给模型。

**端到端打断以助手实际播放为锚点。** 例如“首音频后 1 秒说改成杭州”，不用固定脚本绝对秒数，否则慢模型可能根本没开口。离线轮次检测可用数据集已有双轨；闭环测试用受测模型自己的输出，不能把录制的助手回答当它真的说过。重采样两路时保留对齐，不用加速回放的耗时冒充实时延迟。

**键盘保存事件轨迹。** 记录相对时间、插入/删除/选区/组词/Tab/Enter、草稿修订号、任务状态及实际接纳结果；只保存最终一句话会丢掉 K06—K14 最关键的条件。

一次运行至少记录以下字段；指标取不到时留空，不填零：

```text
case_id / variant / run_id / commit / 主模型与推理等级 / 人设 / System1配置 / ASR后端 / 设备
输入事件及相对时间 / 期望动作 / 原始决策 / 程序约束后的动作 / 实际接纳或播放事件
首个可见意见或可听回答时间 / 已播放范围 / 工具实际参数 / 重复提交数 / 结果与证据路径
```

## 如何评分与定位短板

| 指标 | 定义与用途 |
|---|---|
| 动作正确率 | 每类分别算等待、附和、让出、改向、取消、意见与提交；不能靠某一大类样本稀释错误 |
| 配对成功率 | V04 两个上下文都正确才得分；同时报告真正打断的召回率与附和/旁话误停率 |
| 听感延迟 | 用户最后音素→助手首个实际可听音频；打断另算用户起声→旧音频实际停止。首字到达、收到音频都不能代替扬声器已发声 |
| 键盘反馈延迟 | 最后一次编辑→意见可见；另外记录防抖、决策、主模型生成和渲染。悬浮框里的服务端耗时不等于完整等待 |
| 连续性 | 打断后是否采用新条件、是否丢失/重复/凭空假定已说内容，工具参数是否匹配最新有效要求 |
| 讨论质量 | 意见是否具体、提供新信息且遵循人设；另记重复或打扰次数。无有效意见、自动写入草稿或提交任务都算失败 |
| 任务成本 | 每次成功任务的调用/token、重复工具调用、废弃预计算、用户纠正次数与总完成时间 |

语音的排障顺序：末尾人声→VAD 判停→ASR final→剩余等待→System 1→主模型首正文→分句→TTS 首块→实际播放。保留开始、结束时间看重叠，不能机械累加各段。仅当同一录音、配置与网络条件下替换 ASR，才可讨论本地识别的因果收益；4060 Laptop 与 5080 Desktop 分开记录冷启动、热运行和播放端延迟。

建议第一轮挑 **V01、V03、V05、V12、V15、K01、K02、K03、K04、K07**，每条跑三次查确定性问题；这不足以宣称准确率或 P95。后续扩展说话人、语速、噪声和编辑轨迹，逐类保留样本数与失败记录。先用脚本检查未授权提交、重复提交、工具参数和时序，再人工看语义与听感；模型评分只辅助，不替代实际播放和任务日志。
